# ソロモード（1台で完結）— 現在の設計

`/solo`。**このプロダクトの主経路。**
可否の根拠は [capabilities.md](capabilities.md)、決定の経緯は [log.md](log.md)。

---

## 1. 体験

1. `/solo` を開き「画面を選ぶ」を押す
2. ブラウザのピッカーが出る。**Chrome のタブを選ぶのが最良**（理由は§2）
3. **このページに留まったまま、選んだタブがライブで映る**（実機で確認済み）
4. 分からない所をクリック、またはなぞって囲む。**その瞬間に静止し、その
   ジェスチャーがそのまま印になる**
5. 質問を書いて送っても聞ける。**その場合は送った瞬間に静止する**
6. 共有元のタブに行って操作し、戻ってくると**ライブに復帰**している。また聞ける

ユーザーが下す判断は「どの画面を選ぶか」の1回だけ。教えることは1つも無い。

**静止させるボタンは無い。** ライブ映像に指した対象は答えが返るまでに動いてしまうので
静止画にする必要があるが、**それはこちらの都合であってユーザーに踏ませる手順ではない。**
そもそもこのモードでは見る側と見られる側が同一人物なので、勝手に画面が流れることは
起きない。切り出す瞬間は「ユーザーが行動した瞬間」でよい:

| 行動 | いつ切り出すか |
|---|---|
| クリック・丸囲み | **ジェスチャーが始まった瞬間**（指を置いた時にそこにあったものが対象） |
| 質問を書いて送る | **送った瞬間**（書いている間にページが流れるのは自然なこと） |

## 2. 共有の種類で挙動が変わる（変えざるを得ない）

ピッカーのペインは消せない（capabilities §4-D）ので、3種すべてを扱う。
**約束できることが種類ごとに違うので、UIも変える。**

| 選ばれたもの | 画面に出るもの | なぜ |
|---|---|---|
| **Chrome のタブ**（`browser`）＋フォーカス保持成功 | **ライブ映像**＋「この画面について聞く」 | 留まったまま見られる。行って戻る必要が無い |
| ウィンドウ（`window`） | 静止画。このタブに戻るたびに撮り直す | 前面に出ていないとOSが描画を止める恐れがあり、ライブを信用できない |
| 画面全体（`monitor`） | 離席中に見ていた画面の候補（§4） | このページ自身が映るのでライブは合わせ鏡になる |

`displaySurface` が報告されない場合（Firefox・Safari）は **`monitor` と解釈する**。
誤りの代償が非対称で、タブを monitor と誤ると余分にバッファを積むだけだが、
monitor をタブと誤ると合わせ鏡を大写しにする。

## 3. ライブ表示の要（`setFocusBehavior`）

`getDisplayMedia` は既定で共有先タブへフォーカスを移す。それでは「聞きたい画面を
見に行かされる」ことになり、コパイロットとして成立しない。

`CaptureController` を渡し、**`getDisplayMedia` が解決した直後に同期的に**
`setFocusBehavior("no-focus-change")` を呼ぶ。`await` を挟むとフォーカス決定が先に
起き、以後この呼び出しは例外になる。`lib/screen-share.ts` の該当箇所は
**関数末尾まで同期を維持することが要件**で、コメントにもそう書いてある。

失敗した場合は `keptFocus: false` として記録し、ウィンドウ共有と同じ「行って戻る」
UIに落ちる。黙ってライブを装わない。

## 4. 画面全体を選ばれた場合の候補バッファ

`lib/recent-screens.ts`。**主経路ではない**が、画面全体を選ぶ人のために残す。

- **離席中だけ**1秒間隔で1枚取る。離席の判定は **`document.hidden` のみ**
- 積まれたフレームは定義上すべて「ユーザーが見ていた画面」なので、合わせ鏡を
  検出して捨てる仕組みが不要
- 離れた瞬間には撮らない（OS切替が完了しておらず、写るのはこのページ自身）。
  取得完了時にもう一度離席を確認し、戻っていたら捨てる
- 16×16 **RGB** サムネイルの平均絶対差が 0.12 未満なら同じ画面とみなし、候補を
  増やさずその候補を最新の姿に更新して先頭へ移す（最後に見た順のLRU）。上限12枚
- サムネイルの帯から1クリック、または ←→ キーで選ぶ

**`document.hasFocus()` を離席判定に使ってはいけない。** 画面全体共有では
「フォーカスが無いが画面には映っている」＝写るのは自分であり、しかもChromeの共有バーが
共有開始と同時にフォーカスを奪うため、即座に合わせ鏡が量産される（log.md 参照）。
代償として、別アプリを手前に出しただけ（タブは visible）では何も記録されない。
これは閾値の問題ではなく、自分が中にいるモニタを自分で撮ることの構造的な限界。

## 5. 状態の持ち方

ジェスチャー（指差し・囲み）と回答は、**それが属する1枚のキャプチャと一緒に保持**し、
現在表示中の1枚と一致するときだけ描く。「画面が変わったら消す」処理を書いて回るより、
構造で外れるようにするほうが消し忘れが起きない。

会話履歴（`turns`）の扱い:

| 操作 | 履歴 |
|---|---|
| 別の場所を指す | 切る（指した先が新しい話題） |
| 手でサムネイルから別候補を選ぶ | 切る |
| ライブに戻る／戻ってきて自動でライブに復帰した | **切らない**（「言われた通りにやった、次は?」が続く） |
| 戻ってきて自動で最新に移った | **切らない**（回答を読み直しに来ただけかもしれない） |
| 「新しく聞く」ボタン | 切る |

## 6. 認証トークン

Gatewayは全AI routeでBearerトークンを要求する。**リクエストのたびに
`accessToken()` で取り直す。** ページ読み込み時に取ったトークンを使い回してはいけない
—— 有効期限は約1時間で、このプロダクトはタブを開きっぱなしにして使うものなので、
朝に開いて昼に質問すると「ログインが必要です」と言われる（ログイン画面は無いのに）。
Supabaseクライアントは裏で更新しているので、取り直すのは無料。

## 7. フレームの取得経路

`<video>` から読むと、裏に回ったタブで**同じフレームが返り続ける**恐れがある。
エラーにならず「バッファは埋まっているのに中身が古い」という最悪の形になるため、
`ImageCapture.grabFrame()` でトラックから直接取り、無ければ `<video>` に落ちる。
どちらを使ったかは `?debug` に出す。

`<video>` 要素は共有中ずっとマウントし続ける（差し替えるとストリームが切れる）。
ライブ表示のときは主役、それ以外では隅の小さなサムネイル — 表示していない
`<video>` はデコードが保証されないため、消すことはできない。

## 8. 検証

| 道具 | 分かること |
|---|---|
| `/solo?debug` | 現在のモード・候補数・取得経路・**取得間隔**・各候補のdrift |
| `node scripts/check-solo-buffer.mjs` | `getDisplayMedia` を canvas ストリームに差し替え、3経路すべてを人手なしで通す（24項目） |
| `node scripts/measure-signature-drift.mjs` | 現実的な画面変化に対する署名の差。閾値を勘で決めないため |

実行方法は各スクリプト冒頭。`npm i --no-save playwright` が要る。ユーザーの Chrome を
使うのでブラウザのダウンロードは不要。

**自動検証で分からないこと**: 本当に裏に回ったタブでの取得間隔（テストのタブは
`document.hidden` を偽装しているだけでタイマーが絞られていない）。実画面の `?debug` で
しか測れない。
