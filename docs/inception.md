# 着想の記録 — なぜweb版を作るのか

作成: 2026-08-15 ／ ステータス: ブレストの記録（要件定義は未実施）

この文書は 2026-08-15 の app-ios セッションで行われた発見・実測・ブレストの記録である。
**次のセッションが要件定義をゼロから議論し直さなくて済むこと**が目的で、ここに書かれた
「推奨」は決定ではない。決定は要件定義で行い、その結果がREADMEに昇格する。

## 1. 経緯 — 何が起きたか

app-ios のミラーモード（Mac用送信アプリ→iPhone）開発中に、ユーザーから
「Macにアプリをインストールしないと使えないのが導入のハードルだ。当初の発想は
外付けディスプレイと同じ手軽さだった」という指摘があった。

検証として、ブラウザの `getDisplayMedia`（オンライン会議の画面共有と同じAPI）で
画面を送る試作を app-ios/server 内に作り、**同日中に実機で合格**した。

そこからユーザーのブレストで構想が2段階拡張された。

1. **会議型UI**: Zoom/Meetの画面共有と同じ操作体系で、AIに画面を見せる。
   ピッカーでウィンドウを選ぶ操作が、そのまま「AIに見せる範囲の制御」になる
2. **PC内完結モード**: 別デバイスに送らなくても、同じPCの中でコパイロットパネルを
   開けば「自分の見ている画面を同時に見てくれる目」になる。スクリーンショットを
   手動で撮って貼る本家の操作すら不要になる。音声＋VADと組み合わせれば
   常時同席のアンビエントモードに至る

最後にユーザーが方向を確定した: **「初期フェーズはブラウザ版の方がいい」**。
本格的な開発はこの app-web ディレクトリで新規に始める。

## 2. 実測事実（2026-08-15、app-ios の試作にて）

判定基準は app-ios M4 がネイティブ伝送路に課したものを不変で流用した:
**片道300ms以内・文字が読める**。

| 項目 | 実測値 | 判定 |
|---|---|---|
| 片道遅延（安定後） | **40〜150ms** | ✅ 基準の300msに対し余裕あり |
| 可読性 | 日本語UIの小さな文字まで判読可能 | ✅ ユーザー確認済み |
| 送信レート（タブ前面時） | 14.7 fps（設定15） | 設定どおり出る |
| 送信レート（**タブ背面時**） | **きっかり 1.0 fps** | 🔴 ブラウザのタイマー間引き |
| 帯域（JPEG方式） | 6.1 Mbps で 3.6 fps | H.264（5.84 Mbps で 30 fps）の約3倍非効率 |

### 計測の注意（読み違えないために）

- 試作は**JPEGをHTTPで1枚ずつ運ぶ足場**であり、製品の伝送路ではない。上の数字は
  ブラウザ経路のコストの**上限**である。上限で合格しているので問いは片付いた
- **未解明が1つ残っている**: 遅延が40msから1000ms超まで単調に増えてから回復する現象。
  フレームサイズ（複雑な画面=200KB、単純な画面=77KB）と相関していた。有力仮説は
  「間引かれたタブでの重いJPEG変換」だが未確認。WebRTC移行でこの機構自体が消えるため
  深追いしなかったが、**「遅延が無限に伸びる」は app-ios M4 で致命的と判定した症状**。
  再発したらこの記録に戻ること
- 試作の現物: `../app-ios/server/public/mirror-send.html` / `mirror-view.html` /
  `app/api/mirror/frame` / `scripts/watch-relay.py`

## 3. 会議メタファーが解決するもの

単なるUIの見た目ではなく、3つを同時に解決する。

1. **学習コストの借用。** 「共有ボタン→ピッカーで選ぶ→指して話す」は全世界が
   習得済みの操作。教えることがゼロ
2. **プライバシーの文法の借用。** 「このウィンドウだけ共有」を選ぶ操作が、そのまま
   「AIに見せる範囲」のユーザー自身による制御になる。B2Bで必ず聞かれる
   「全部見られるのか？」への答えがUIに最初から組み込まれている
3. **メンタルモデルの転換。** ツールを「使う」のではなく、画面が見える相手と
   「同席する」。アンビエントモード（受信メールを見て「これ何て言ってる？」と聞ける）は
   このメタファーの自然な延長であって別機能ではない

将来の扉: 会議なら**人間も同席できる**。ヘルプデスク担当者が同じ「会議」に入り、
AIが一次対応・人間が二次対応、という形が同じ構造のまま作れる（今は扉の記録のみ）。

## 4. PC内完結モードの技術的骨格

**ストリーミングが丸ごと不要になる**のが最大の発見。別デバイスへ送らないなら、
`MediaStream` を保持したまま**質問された瞬間に1フレーム取れば足りる**。
§2で苦労した間引き・遅延・中継・帯域の問題が全部消え、解析コストも質問数に比例するだけ。

既知の力学2つと、その解:

- **自分自身の写り込み / パネルが対象を隠す問題** → **ウィンドウ単位の共有を既定にする**。
  ウィンドウ共有は重なり順に関係なくそのウィンドウの中身を写すので、パネルがどこに
  あっても汚染しない。全画面共有が要る場面は Document Picture-in-Picture（Chrome）が逃げ道
- **実画面にハイライトを描けない問題**（ブラウザは他アプリの上に描画できない）→
  「いま撮った画面のスナップショットに枠を打ってパネル内に表示」。これは app-ios
  カメラモードと同じ形で、体験として成立することは実証済み

## 5. なぜ初期フェーズはweb版か（ユーザー判断＋裏付け）

- **ユーザー側**: 準備ゼロ。困ったときだけ開いて閉じる。全OS（社内システムはWindowsが
  多く、B2Bではむしろ本命）。URLで配布でき、URLにコンテキストパックを紐づければ
  「社内ポータルの『画面を見てもらう』ボタン」が作れる — 汎用チャットAIに真似できない形
- **開発側**: 審査もTestFlightも署名もnotarizationも不要。デプロイ即日反映。
  営業デモがリンク1本
- **資産側**: 解析・プロンプト・パックという中核はサーバー側にあり全クライアント共有。
  web版を先行させてもネイティブの資産は無駄にならない

**ネイティブが勝ち続ける点**（web版は追わない）:

- **召喚速度**: ホットキー即時 vs タブを開いて共有する数秒の儀式。毎日何十回も呼ぶ
  ヘビーユースではネイティブが勝つ。頻度で棲み分ける
- **見ている範囲の持続性**: ウィンドウ共有は対象アプリを切り替えても付いてこない。
  アンビエントの「常に見ていてくれる」には全画面共有が必要で、プライバシーの文法と
  トレードオフになる（設計で選ばせる）
- **AX実測座標・実画面オーバーレイ・リモート操作**

**ネイティブとの連携は実在する定番パターンで拡張できる**: ネイティブ常駐が localhost に
小さなHTTP/WSサーバーを立て、webページがそこへ話しかける（Zoom・1Password等が実際に
使う構造）。**同じweb UIのまま、ネイティブがあればAX・オーバーレイ・操作が追加解錠される**
漸進的な設計が可能。v0では実装しないが、これを不可能にする設計だけは避ける。

## 6. 再利用地図 — 車輪を再発明しないために

### app-mac（本家・配布済み `v0.2.2`）から

| 資産 | 場所 | web版での扱い |
|---|---|---|
| **Gateway本番運用**（認証・quota・課金・fallback・SSE） | `web/`一式、api.universal-io.com | 合流先の最有力候補（§7-1） |
| **匿名ゲスト設計**（ログインなしで約20回） | README「ゲストプレビュー」 | **web版の「準備ゼロ」とそのまま同型**。設計を流用する |
| Vision契約（image+question+turns+candidates+context、SSE delta→result、`meta.fallback_used`） | `docs/api-contract.md` | wire形式の互換を最初から意識する |
| Skills（製品単位の知識層。データであり制御フローに触れない・常に可視） | README「操作」節 | パックと二重発明しない（§7-2） |
| 設計思想（ユーザー起点世界モデル・ハーネスエンジニアリング・明示意図がスコープを決める） | `docs/design-philosophy.md` | **思想の正本。web版もこれに従う** |
| R11不変条件（無音で終わらない・全操作に期限・診断可視） | README R11節 | 初日から採用（§8の授業料参照） |
| プライバシー規律（store:false・ZDR・画像/回答は保存しない・usage最小） | README「データ保存」 | そのまま踏襲 |
| モデル選定の教訓（開いたプルダウンを読めないモデルは案内に使えない） | `docs/guidance-accuracy-plan.md` | モデル評価時の必読 |
| ピッチ・ビジョン文書 | `docs/pitch/` | 対外説明の語彙はここから |

### app-ios から

| 資産 | 場所 | web版での扱い |
|---|---|---|
| `/api/analyze` 最小サーバー（SSE・パック注入・**tap_point/region**） | `server/` | プロトタイプの解析先候補（§7-1） |
| **座標の授業料**（画像サイズ明記・縮小1536・誤差はバイモーダル・座標はモデルに目測させない） | `docs/lessons-from-app-mac.md` §3-4、HANDOFF | **全部そのまま効く。再履修しない** |
| タップ＋丸囲みUIと「送った座標を同じ変換で描き戻す」計測 | `ios/.../MirrorView.swift` | UIパターンとして移植 |
| ブラウザ送信の試作一式と計測器 | `server/public/`、`scripts/watch-relay.py` | web版の出発点。ただし製品はWebRTC/オンデマンド取得へ |
| デバッグ画像保存＋描画（`UIO_DEBUG_CAPTURE_DIR`→`draw-boxes.py`） | `server/` | 座標問題の切り分けに必須。初日から有効化 |

### 収束に注意すべき二重発明（既に2つある）

- **知識注入**: app-mac「Skills」（セクション構造・製品判定・可視化）と
  app-ios「コンテキストパック」（Markdown 1枚）。**web版で3つ目を作らない。**
  どちらへ寄せるかは要件定義で決める
- **明示スコープ**: app-mac「Focused Vision（選択がスコープ）」と app-ios「丸囲み
  （regionがスコープ）」は同じ思想の別実装。design-philosophy の権限階層
  （明示操作＞取得情報）が両方の正本であり、web版のクリック/丸囲みも同じ階層に従う

## 7. 未決の問い（要件定義セッションの議題）

1. **サーバーはどれか。** 選択肢: (a) 本番Gatewayの3番目のクライアントになる /
   (b) app-ios の最小サーバーに乗る / (c) 新造。
   推奨の方向: **プロトタイプは(b)**（region対応済み・最小・即動く）。ただし
   **封筒（request_id・SSE delta→result・エラーcode体系）を最初からGateway互換の形**にし、
   配布段階で(a)へ合流して認証（匿名ゲスト）・quota・課金を借りる。
   ゼロベース設計の自由と連携可能性を両立させる線がここ
2. **知識注入はSkillsかパックか**（§6参照）
3. **画面取得の方式。** PC内完結=オンデマンド1フレーム（実装最小）を先に作るか、
   別デバイス=ストリーミング（WebRTC）を先に作るか。ブレストの流れはPC内完結が先
4. **音声・アンビエントをどのフェーズに置くか**（VAD・streaming ASRはapp-macでも未着手の
   別プロジェクト級。v0に入れない前提で議論を始めるのが妥当）
5. **名前とドメイン。** 本家サイト・Gatewayとの関係（サブドメイン? 同居?）
6. **app-ios の扱い。** ミラーモード（MPC）はネイティブ精度経路として残す。
   app-ios/server の mirror-* 試作はweb版へ引っ越すのか、実験の記録として凍結するのか
7. **ゲストのトークン設計。** 「準備ゼロ」と「乱用防止」の両立。app-macの匿名サインイン＋
   guest枠の流用が最短に見えるが、レート制限・画像サイズ上限も含めて要件定義で確定する

## 8. web固有の支払い済み授業料（2026-08-15、1日分）

すべて**例外を投げず、正解の顔をして間違えた**。app-ios の授業料と同じ形。

| 罠 | 対処 |
|---|---|
| `getDisplayMedia` はsecure contextのみ。LAN IPのhttpでは**共有ボタン自体が出ない** | 開発は `localhost`、配布はHTTPS必須 |
| **背面タブのタイマーは毎秒1回に間引かれる**（15fps設定→きっかり1.0fps） | JSタイマーでフレームを刻まない。WebRTC（ネイティブ側で動く）かオンデマンド取得 |
| `display:none` の `<video>` はデコードが保証されない | プレビューとして小さく表示し続ける（取得が生きている証拠も兼ねる） |
| **idセレクタの `display` 指定が `[hidden]` に勝つ**。ボタンは反応するのに画面が変わらない | `[hidden] { display: none !important }` をリセットに入れる。「無音で失敗するUI」の一種 |
| 中継が古いフレームを「生きている映像」の顔で返す | 鮮度チェック（5秒）で保留に切り替える。古い絵は無いより悪い |
| 計測器がゼロの列を出すと「経路が死んでいる」と誤読される。実際は**送信側を起動していなかっただけ** | 計測器は「NOT SENDING — nothing to measure」と状態を言い、無データの要約を拒否する |

## 9. 最初のマイルストーン案（要件定義のたたき台）

**M1: PC内完結の会議型プロトタイプ。** 1ページで、共有→（クリック or 丸囲み）→
スナップショットに枠と解説が出る、まで。

- 画面取得はオンデマンド1フレーム（ストリーミングなし）
- 解析は app-ios `/api/analyze` へ（tap_point/region/candidatesは対応済み）
- 合格ライン: 質問から最初の一文表示まで**体感でチャットAIに貼るより速い**こと、
  枠が対象に命中すること（app-iosの実測では命中率8割が出発点）
- ここで会議メタファーのUX仮説（ピッカー・ウィンドウ共有既定・パネル配置）を検証する

M1が立てば、別デバイスパネル（M2〜）・音声（M3〜）・Gateway合流（配布前）と進む。
順序も含めて要件定義で確定する。
