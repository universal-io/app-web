# アイディエーション — ブラウザ単体でどこまでできるか（検証済みアイデア集）

最終更新: 2026-08-17

**目的: 同じ検討をもう一度ゼロからやらないための記録。**
ここにあるのは会話ベースの机上検証（モデル知識による調査）であり、コードでの実証は
まだしていない。API名・対応バージョンは実装着手時に必ず一次情報で再確認すること。

## 1. 前提となる非対称性 — なぜ「映せるのに描けない」のか

`getDisplayMedia` で得られるのは画面の**映像ストリーム**であって、画面への
アクセス権ではない。ピクセルは一方通行で入ってくるだけ。一方、Webページが描画
できる領域は自分のタブ（と自分が開いたウィンドウ）の内側に厳密に限定される。

「〇〇が画面を共有しています。共有を停止」のバーが出せているのは、あれが
**Webページではなくブラウザ本体（ネイティブコード）がOSレベルで出している
別ウィンドウ**だから。この能力をWebページに渡すAPIは存在せず、渡さない理由は
明確（悪意あるページがOSのパスワードダイアログ等の偽UIを他アプリの上に重ねられる
とフィッシングし放題になる）。**仕様の穴ではなく設計思想**なので、将来の解禁を
待つ戦略は成立しない。

## 2. 実画面へのオーバーレイ — 結論: 純Webでは不可

| 手段 | 他アプリの上に出せる | 透明・位置指定 | Webだけで完結 |
|---|---|---|---|
| 通常のDOM | ✗ | ✗ | ✓ |
| Document Picture-in-Picture | ✓（矩形の不透明窓） | ✗ | ✓ |
| 送信ストリームへの合成 | 受信側の画面にのみ | ✓ | ✓ |
| Electron / Tauri | ✓ | ✓ | ✗ |

- **Document PiP（Chrome 116+）**: 任意のHTMLを入れた常時最前面のフローティング
  ウィンドウをWebページが開ける。「PC内完結」形態のコパイロットパネルを他アプリの
  上に浮かべ続ける用途には実用的。ただし矩形・不透明・クリック透過不可で、
  実画面上の特定要素を指し示すことはできない。
- **ストリーム合成**: canvasでキャプチャ映像に注釈を描いて `canvas.captureStream()`
  で送り直せば、**受信側**にはオーバーレイ付き映像を見せられる（会議ツールの注釈は
  この方式）。共有者本人の実画面には何も出ない。
- **真の透明・クリック透過・位置指定オーバーレイ**は Electron/Tauri の領分で、
  それは app-mac が既にやっている。**web版はここを追わない**（READMEの
  「ネイティブが構造的に勝つ点は追わない」と同じ結論に別ルートで到達）。

## 3. 共有画面への操作の送り返し — 公式は1種類、クリックは3ルート

### 公式に存在するもの: Captured Surface Control API（Chrome 136+）

キャプチャ中の**タブ**に対して `CaptureController` 経由で**ホイールスクロールの
転送とズーム操作**ができる。「アプリ内に映っているミニ画面をスクロールすると
実タブがスクロールする」は純Web・拡張なしで実現可能。
意図的にスクロール＋ズーム止まりで、クリック・キーボード転送は標準APIとしては
今後も来ない可能性が高い（§1と同じセキュリティ理由）。

### クリックまで届かせる3ルート

| ルート | 仕組み | 強み | 弱み |
|---|---|---|---|
| A: 軽量拡張機能 | Webアプリが「顔」、拡張が「手」。`chrome.debugger`（CDP `Input.dispatchMouseEvent`）で実タブに信頼された入力を注入 | ユーザーの実セッション（ログイン済み画面そのもの）を操作できる。事実上のブラウザ内Playwright | インストール1回が要る（ネイティブアプリよりは遥かに軽い） |
| B: クラウドブラウザ埋め込み | サーバー側のPlaywright操作可能ブラウザをWebRTCでページ内にストリームし入力転送（Browserbase等の方式） | インストールゼロでフル操作 | **別セッション**なのでログイン壁が本質的（GA等はここで詰む） |
| C: ローカルCDP直結 | `--remote-debugging-port` ＋ `--remote-allow-origins` 付きで起動したChromeに、ページから `ws://localhost:9222` へ直接WebSocket | 拡張すらなしで自ブラウザの他タブをフル操縦できる | 起動フラグ必須・セキュリティ的に危険。パワーユーザー向けデモ/検証モード以上にならない |

座標は `<video>` の表示サイズと共有面の実解像度の比率で実座標に変換できるので、
「ミニ画面をタップ→実タブで発火」も「ビジョンモデルが座標を返す→エージェントが
押す」（computer use と同型）も、どのルートでも同じコードに乗る。

## 4. ピッカー（共有対象の選択UI）の制約と近似解

- **ピッカーの中身と並び順はブラウザの管轄で、Webアプリからは一切制御できない。**
  「共有ボタン→直近のタブが大写し→スワイプで次候補」という理想UXは、そのままは
  実装不可。
- **近似解（重要）: 画面全体を1回共有してしまえば、以後ユーザーが Cmd+Tab で
  前面に出したものがそのまま映る。** つまり「候補の巡回」はOSのタスク切替そのもので
  代替でき、再訪時には「直近に触っていた画面」が自動的に映っている。理想UXの
  体験価値の大半はこれで出る。
- タブ共有の場合は `surfaceSwitching: 'include'` を渡すと、共有開始後にユーザーが
  ブラウザUIの「代わりにこのタブを共有」で対象を切り替えられる（ピッカー再表示不要）。
- その他のヒント: `preferCurrentTab`、`displaySurface`。

## 5. 現時点で最有力の方向 — 入口体験（ゼロインストールで初手解決）

正規ルート（標準APIのみ）で成立し、かつ製品の存在理由（URLを開くだけ）と一致する
方向。すでに実装済みの部分が多い。

1. 何かに詰まる → このサービスのタブを開く（or 開いてある）→「聞く」
2. 聞きたい画面が大写しになる（§4の近似解: 全画面共有なら直近に触っていた画面が
   そのまま映っている）
3. わからない場所をタップ／囲み、チャットで質問する
4. 元の画面に戻って操作し、再訪すると**差分を検出して続きを説明**してくれる
5. LLM側のスクリーニング: 履歴・注入コンテキスト（パック/Skill）から「ユーザーが
   聞きたいのはこの画面・この課題」をある程度推定できる

この体験があって初めて「ネイティブ版をわざわざインストールする価値」が伝わる、
という入口（ファネル）としての位置づけ。

## 再トライするときの着手順

1. **Captured Surface Control を足す** — 数十行で済み、ミニ画面が「触れるテレビ」に
   なって体験が一段変わる。純Webのまま
2. **最小拡張機能（クリック転送のみ）を試作** — ルートAの検証。実セッションを
   操作できるかが焦点
3. **Document PiP でPC内完結パネルを常時最前面化** — 別デバイス不要の
   コンパニオン形態
4. ルートB/Cは、それぞれ「ログイン壁を許容できるユースケース」「デモ用途」が
   明確になってから
