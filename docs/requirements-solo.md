# 要件定義 — PC内完結（ソロ）モード

最終更新: 2026-08-17
位置づけ: docs/ideation.md §5「入口体験」の要件定義。**現在の本命。**
2台構成（M2）はそのまま残し、並行して存在する。

---

## 0. 北極星シナリオ（これができたら成功）

> 困っている人にこのURLを送る。その人は訳もわからないままボタンをタップする。
> すると自分が困っていた画面（あるいは直前まで見ていた画面）が大写しになる。
> わからない場所をタップして聞いたらすぐにわかった。ついでに気になっていたことを
> いろいろ聞いたら全部わかった。—— この体験でリピートするようになる。

導出される制約:

- **インストール・ログイン・前準備・専門用語ゼロ。** URLを開く以外の学習コストを課さない
- **初回でも「聞きたい画面が映るまで」を最短にする。** 2回目以降は2アクション以内で
  回答に着手できること（下記 §6 受け入れ基準）
- **正規ルートのみ**（標準Web API）。拡張機能・起動フラグ・クラウドブラウザは使わない
  （それらの検討結果は ideation.md §3 に記録済み。ここでは追わない）

## 1. スコープ

| 含む（M3） | 含まない（先送り先） |
|---|---|
| 1台のPC内で完結する「聞く」体験 | 実画面へのオーバーレイ（ideation §2で不可と結論） |
| 画面全体共有＋直近画面の候補提示 | Captured Surface Control（操作転送。次段） |
| 既存のタップ/囲み/チャット/枠表示の再利用 | Document PiP パネル（P2実験） |
| ウィンドウ共有時のライブ＋固定 | 音声入力・アンビエント |
| | LLMによる「聞きたい画面」推定（P2。まず新しさ順で足りるか測る） |
| | 2枚画像の差分説明（Gateway契約の拡張が要る。§8） |

## 2. UXフロー

### 2-1. 入口

- トップページ（`/`）の第一ボタンをソロモードにする:
  **「いま見ている画面について聞く」**。2台構成（QR/コード）は第二の導線に下げる。
  URLを送られた人が最初に押すボタン＝ソロ、が北極星シナリオの要請
- 実装はまず独立ルート `/solo` で行い、動いたらトップの第一導線にする
  （M2の画面を壊さずに反復するため）

### 2-2. 共有開始（初回のみの儀式）

1. ボタンを押すと `getDisplayMedia` のピッカーが出る
2. ピッカーには次のヒントを渡す（すべて標準オプション。非対応ブラウザでは無視される
   だけなので分岐不要）:
   - `video: { displaySurface: "monitor" }` — 「画面全体」ペインを最初に出す
   - `selfBrowserSurface: "exclude"` — 自分自身のタブを候補から消す（選ぶと合わせ鏡
     にしかならない選択肢を、そもそも見せない）
   - `surfaceSwitching: "include"` — タブ共有を選んだ人が後から対象を切り替えられる
3. 共有が始まったら、ページは1つだけ指示を出す:
   **「わからない画面に戻ってください。このタブに戻ってくると、その画面が写っています」**
   - この一文が唯一の「教えること」。以後の再訪では表示しない

### 2-3. 戻ってきた瞬間（体験の核）

- ユーザーがこのタブに戻ると、**直前まで見ていた画面が静止画で大写しになっている**
  （ライブ映像ではない。ライブは自分のタブ＝合わせ鏡しか映らない。§3-1）
- 大写しの画面が目的のものでなければ、**スワイプ（またはクリック/矢印キー）で
  ひとつ前の「別の画面」に移れる**。候補は新しい順。ideation §4の
  「直近に触っていた画面を順番に出す」は、ピッカーでは実現不可だが
  **自前の候補バッファでなら実現できる**（§3-2）— これがこのモードの発明点
- 候補は視覚的に十分異なる画面だけに間引かれる（同じ画面のスクロール差分で
  候補が埋まらないように）

### 2-4. 聞く

- 大写しの静止画に対して、既存の `Snapshot` の操作系をそのまま使う:
  タップ＝「このコントロール」、なぞって囲む＝「この中のもの」、チャット入力、
  返ってきた枠と解説の表示。**新しいジェスチャーは発明しない**（app-ios から
  持ってきた現行の型を維持）
- 続けて同じ画面の別の場所も聞ける（既存の `point()` の挙動どおり、指し直しで
  話題がリセットされる）

### 2-5. 行って、戻って、また聞く

- 元の画面に戻って操作 → このタブに再訪 → **最新の画面が既に大写し**（2-3と同じ）
- 会話履歴（`turns`）は「同じ話題の続き」として引き継ぐ。新しいキャプチャに対する
  質問でも直前のやりとりをテキストで同送し、「さっきの続きです」が通じるようにする
  - 話題を切るのはユーザー操作（「新しく聞く」）またはヒューリスティック
    （候補を大きく遡った場合）。どちらにするかは実装時に軽い方から試す
- 画像2枚を並べた真の差分説明はGateway契約にないため M3 では**やらない**（§8）

### 2-6. 終了

- タブを閉じる、またはブラウザの「共有を停止」バーで終わる。既存実装と同じく
  `track.ended` を拾って全状態を破棄する。**候補バッファも含めて何も残さない**

### 2-7. ウィンドウ共有を選んだ場合（分岐）

`track.getSettings().displaySurface` で判定する。

- `"monitor"`（画面全体）→ 上記の候補バッファUX
- `"window"` / `"browser"`（特定ウィンドウ・タブ）→ 合わせ鏡が起きないので、
  **ライブ映像＋「この画面について聞く」ボタン**（watch ページと同じ型）で足りる。
  候補バッファは不要
- どちらの選択も正解として扱う。「このウィンドウだけ共有」はZoomで体得済みの
  プライバシーの文法であり（README）、矯正しない

## 3. 技術設計

### 3-1. 自己鏡像問題（このモードの主敵)

画面全体を共有して自分のタブに戻ると、映像には自分のタブが映る（合わせ鏡）。
つまり**「戻ってきた瞬間に見たい画面」は、戻ってきた時点ではもうライブには無い。**
過去のフレームを持っておくしかない。これが候補バッファの存在理由。

- タイミングの罠: `visibilitychange`（visible）を受けてからフレームを取るのでは遅い。
  OSの画面切替が先に完了しているので、取れるのは自分のタブ。
  **バッファはタブが hidden の間に積む**
- hidden 中のフレームは定義上すべて「ユーザーが見ていた画面」なので、自己除外の
  判定ロジックは要らない。**visible の間は積まない**、それだけでよい

### 3-2. 候補バッファ

- タブが hidden になったら、タイマーで `captureFrame`（既存関数）を回して
  リングバッファに積む。visible に戻ったら止める
- **バックグラウンドタブのタイマーは 1fps に絞られるが、それでよい。**
  inception §2 の教訓（タイマー駆動ストリーミングの失敗）は 15fps の動画配信を
  タイマーでやろうとした話であり、ここは「数秒に1枚の静止画」で成立する用途。
  絞られた 1fps はむしろ上限として都合がよい。この違いは実装コメントに明記する
- 間引き: 新フレームを縮小サムネイル（例: 32×32相当）で直前候補と画素比較し、
  差が閾値未満なら**候補を増やさず最新版として置き換える**（同じ画面の最新状態を
  保ちつつ、スクロールで候補が埋まるのを防ぐ）
- 上限: 明確に異なる候補を N 枚（初期値 8。測って調整）。JPEG dataURL で
  1枚 200〜500KB 程度なので、メモリは高々数MB
- **プライバシー規則（ファミリー共通規則の適用）**: バッファは in-memory のみ。
  送信されるのは「ユーザーが選び、聞くと決めた1枚」だけ。共有停止・タブ閉鎖で
  即破棄。この規則は UI にも一文で表示する（「選んだ画面だけが送信されます」）

### 3-3. 既知のリスクと対策

| リスク | 内容 | 対策 |
|---|---|---|
| Intensive throttling | Chromeは hidden 5分超のタブのタイマーを1回/分まで絞ることがある | まず実測（§7の道具）。1枚/分でも「最後にいた画面」は撮れているので体験は壊れにくい。壊れる実測が出たら Worker + `MediaStreamTrackProcessor` への移設を検討（M3では負わない） |
| Safari/Firefoxの挙動差 | ピッカーオプションの無視、hidden時スロットリングの差 | 一次ターゲットは Chrome/Edge。他は「動けば良し」で、動かない場合の理由表示だけ整える（R11: 無音で終わらない） |
| ピッカーの一手間 | 初回に必ずOSピッカーが出る。省略は不可能（設計思想。ideation §1） | 2-2のヒント3点で選択を最短化。共有はタブが生きている限り持続するので、儀式は初回のみ |
| モバイル | `getDisplayMedia` が無い | 既存の `screenShareUnavailableReason()` の分岐を流用し、2台構成（QR）への誘導を出す |

## 4. 検討した代替案と判断

| 代替案 | 判断 | 理由 |
|---|---|---|
| スクリーンショットを貼る/アップロード（`paste`/drag&drop） | **M3cで併設** | 権限もピッカーも不要でモバイルでも動く最強のフォールバック。ただしOSのスクショ操作を知らない人が対象なので主経路にはしない |
| Document PiP でパネルを浮かべ、問題の画面から離れずに聞く | P2実験 | 手数は最小になるが、PiP窓自体が画面に映り込む・小窓での読解体験など未知が多い。候補バッファUXが立ってから足す |
| 拡張機能・ローカルCDP・クラウドブラウザ | 今は追わない | ideation §3 に記録済み。「準備ゼロ」の北極星と矛盾する |
| ライブ映像を主とし「固定」ボタンで聞く（watchページの型をそのまま） | 画面全体共有では不成立 | 合わせ鏡（§3-1）。ウィンドウ共有の分岐（2-7)でのみこの型を使う |
| LLMで「聞きたい画面」を最初に推定 | P2 | 候補が新しい順に並ぶだけで1〜3枚目に正解が来る見込みが高い。まず測る（測ってから決める） |

## 5. 画面仕様（M3の最小）

```
[/solo 共有前]
  「いま見ている画面について聞く」ボタン
  （モバイル等では理由＋2台構成への誘導）

[共有直後・初回のみ]
  「わからない画面に戻ってください。このタブに戻ってくると、その画面が写っています」

[再訪時]
  ┌─────────────────────────┐
  │  直近の画面（静止画・大写し）              │ ← タップ/囲みで即質問
  │                                          │
  │  ◀ ▶ 候補切替（新しい順、間引き済み）      │
  ├─────────────────────────┤
  │ 回答パネル / 質問入力（watchページと同じ）  │
  │ 「選んだ画面だけが送信されます」            │
  └─────────────────────────┘
```

## 6. 受け入れ基準（GAシナリオで検収する）

前提: Google Analytics で「デバイス別の見方」がわからない人。

1. **初回**: URLを開く → ボタン → ピッカーで画面全体 →（指示に従い）GAに戻る →
   このタブに戻る → **GAの画面が大写しになっている** → わからない場所をタップ →
   解説と枠が返る。ここまでユーザーの意思決定は「画面全体を選ぶ」の1点のみ
2. **再訪**: GAで操作 → タブに戻る（1アクション）→ 最新のGA画面が大写し →
   タップ（2アクション目）→ 回答着手。**再訪は2アクション以内**
3. 直前に別の画面（例: メール）を経由してから戻っても、候補を1〜2回戻せば
   GAの画面に到達できる
4. 10分放置してから戻っても、「最後にいた画面」の候補が出る（throttlingの実測含む）
5. ブラウザの「共有を停止」で終えたとき、ページが破綻せず初期状態に戻る（既存挙動）
6. 送信された画像が「ユーザーが選んで聞いた1枚」だけであることをNetworkタブで確認できる

## 7. 検証の道具（残課題 #2 と同根。先に作る）

## 10. 未決の問い

- 話題の継続と切断の境界（2-5）: 明示ボタンか、候補を遡ったら切るか。実装時に軽い方から
- 候補の提示形態: 大写し＋端に前候補をチラ見せ（スワイプ暗示）か、フィルムストリップか
- `visibilitychange` と `pagehide`/`blur` のどれで hidden 判定するか（別アプリに
  切り替えてもタブが visible のままのケース: 別モニタ・ウィンドウ並置。この場合
  ライブに自タブは映らないので、visible 中も低頻度で積む選択肢がある。実測で決める）
