# コンパニオン（スマホ・タブレットで見る）— 現在の設計

`/` の「スマホやタブレットで見る」→ QR → `/companion/[roomId]`。**実機で動作している。**

**別モードではない。** 本体（`/`）が掴んでいるのと同じ共有ストリームを部屋に流し、
第二の端末がそれを見るだけ。PC側は普段どおり作業を続け、
**作業画面を1ピクセルも奪わない**のが固有の強み。可否の根拠は [capabilities.md](capabilities.md)。

---

## 1. 体験

PCの `/` で「QRコードを表示」（画面全体の共有を勧める）→ QRまたは8文字コードで
スマホが参加 → **最初の映像が届いた時点でライブ表示と初回説明が始まる**。別の
「この画面について聞く」段階は置かない。既定の手のひらでライブ映像を拡大・移動し、
気になる場所をタップするとその瞬間で固定して質問する。範囲を伝えたいときだけペンへ
切り替えて囲む → 解説と枠。

| 役割 | 端末 | できること |
|---|---|---|
| 共有する側 | PC | 共有を開始・停止するだけ |
| 見る側 | スマホ／タブレット | ミラーを拡大・移動 → タップ／囲む → その瞬間で止まり質問する |

**普段はミラーリング、質問したい瞬間だけ静止画に固定する。** 動いている映像に指を
差しても、答えが返るまでに対象が動いて消えるため成立しない。

### スマホの画面構成

- **縦持ちが正。** 横長のPC画面を中央に全体表示し、上下の余白を説明と入力に使う
- **手のひらが既定。** 1本指で移動、ピンチで最大8倍、静止タップでその場所を質問する
- **ペンは明示的に選ぶ。** 1本指で囲み、2本指はどちらのツールでも拡大・移動に使う
- ライブ映像と静止画は同じキャンバスを共有し、切り替えても見ていた倍率と位置を保つ
- 拡大するのは共有映像だけ。ライブ表示、ツール、解説、入力欄は端末上の大きさを保つ
- 注釈は**座標と囲む範囲だけ**を映像の拡大へ追従させる。枠線、手描き線、パルス、
  キャプションは逆倍率を掛け、何倍に拡大しても端末上の太さ・文字サイズを保つ
- 解説バブルは下中央が初期位置であり固定場所ではない。空の入力状態から常にグリップを
  表示し、会話が長くなったときも同じバブルを指で好きな位置へ移動できる
- コンパニオン経路ではSafariのページ拡大を止める。他のページでは通常のブラウザ拡大を保つ

## 2. なぜ質問するUIが別端末にあるのか

質問するUIを共有される側と同じ画面に置くと、**監視対象の上に監視用UIが載る**。
会議で言えば発表者が自分の共有画面を指差して自分に説明する形で、役割が混線する。
この構造的な問題がコンパニオンを生んだ。

（1台での利用はこれをタブ共有で解いた。共有対象が別タブなら、質問UIは監視対象の上に
載らない。両者は同じ問題への別解であり、どちらも成立する。）

## 3. 決定事項

1. **固定するフレームはミラー映像をそのまま止める。** 共有元へ高解像度を要求しない
   （往復が入ると「その瞬間」がズレる）。ミラー経由でも日本語の小さい文字が判読できる
   ことは実測済み（capabilities.md §2）
2. **伝送路は WebRTC（P2P）、シグナリングは Supabase Realtime broadcast。**
   専用サーバーは不要で、`@supabase/realtime-js` は `supabase-js` の依存として既に入って
   いる。映像は端末間を直接流れ、こちらのサーバーを通らない（プライバシーとコストの両方で有利）
3. **見られる側と見る側は同一人物**を前提とする（会議に自分のPCとスマホの両方から
   入るのと同じ）。この前提が §5 の判断を支えている
4. **Gatewayの変更は不要。** 質問するのは見る側の端末で、既存の `pointer` /
   `annotations` 契約をそのまま使う

## 4. ペアリング

PC側（`/` のQRボタン）が部屋を作ってQRを表示し、スマホはURLで入る。**手入力できる8文字コードも必ず
併設する** — iOSはカメラから開いたリンクをSafariで開き、ホーム画面に追加した
アプリには渡さない。つまりホーム画面アプリを開いた端末では、QRを読んでも当のアプリに
入れない。手入力が唯一の確実な導線。

スマホ側もGoogleサインインが要る（質問するのはそちらで、枠を消費するのもそちら）。
同じアカウントでサインインすれば、PC側と同じ枠になる。

## 5. 🔴 公開前に必ず戻ること

### 部屋コードの強度

部屋IDは**8文字・約39bit**。総当たりされない水準ではない。128bitのhexから意図的に
弱めたのは §4 の手入力導線のためで、**現在これが許容できるのは、部屋が一時的であり、
かつ見る側と見られる側が同一人物という前提（§3-3）があるからに過ぎない。**
他人に部屋を見せる段階へ進む前に、必ずこの判断を見直すこと。

### その他

- **TURNサーバー未設置。** 同一LANならP2Pはほぼ成功するが、別ネットワーク間や
  symmetric NAT では中継が要る。現在は失敗時に理由を表示するのみ（無音で失敗させない）
- **レート制限がGatewayに無い**（プロバイダの429転写のみ）
