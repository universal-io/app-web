# 2台構成モード（PCを共有し、スマホから質問）— 現在の設計

`/` の第二導線と `/watch/[roomId]`。**実機で動作している。**
ソロモードが主経路になった今、こちらは**作業画面を1ピクセルも奪わない**という
固有の強みで残る。可否の根拠は [capabilities.md](capabilities.md)。

---

## 1. 体験

PCで共有 → QRまたは8文字コードでスマホが参加 → ミラーを見て、聞きたい瞬間に
固定 → なぞって囲む／タップ → 解説と枠。

| 役割 | 端末 | できること |
|---|---|---|
| 共有する側 | PC | 共有を開始・停止するだけ |
| 見る側 | スマホ／タブレット | ミラーを見る → その瞬間で止める → 指して質問する |

**普段はミラーリング、質問したい瞬間だけ静止画に固定する。** 動いている映像に指を
差しても、答えが返るまでに対象が動いて消えるため成立しない。

## 2. なぜ質問するUIが別端末にあるのか

質問するUIを共有される側と同じ画面に置くと、**監視対象の上に監視用UIが載る**。
会議で言えば発表者が自分の共有画面を指差して自分に説明する形で、役割が混線する。
この構造的な問題が2台構成を生んだ。

（ソロモードはこれをタブ共有で解いた。共有対象が別タブなら、質問UIは監視対象の上に
載らない。両者は同じ問題への別解であり、どちらも成立する。）

## 3. 決定事項

1. **固定するフレームはミラー映像をそのまま止める。** 共有元へ高解像度を要求しない
   （往復が入ると「その瞬間」がズレる）。ミラー経由でも日本語の小さい文字が判読できる
   ことは実測済み（capabilities.md §2）
2. **伝送路は WebRTC（P2P）、シグナリングは Supabase Realtime broadcast。**
   専用サーバーは不要で、`@supabase/realtime-js` は `supabase-js` の依存として既に入って
   いる。映像は端末間を直接流れ、こちらのサーバーを通らない（プライバシーとコストの両方で有利）
3. **見られる側と見る側は同一人物**を前提とする（会議に自分のPCとスマホの両方から
   入るのと同じ）。この前提が §5 の判断を支えている
4. **Gatewayの変更は不要。** 質問するのは見る側の端末で、既存の `pointer` /
   `annotations` 契約をそのまま使う

## 4. ペアリング

PC側が部屋を作ってQRを表示し、スマホはURLで入る。**手入力できる8文字コードも必ず
併設する** — iOSはカメラから開いたリンクをSafariで開き、ホーム画面に追加した
アプリには渡さない。つまりホーム画面アプリを開いた端末では、QRを読んでも当のアプリに
入れない。手入力が唯一の確実な導線。

スマホ側は自分の匿名セッションでGatewayを呼ぶので、利用枠は質問した側が消費する。

## 5. 🔴 公開前に必ず戻ること

### 部屋コードの強度

部屋IDは**8文字・約39bit**。総当たりされない水準ではない。128bitのhexから意図的に
弱めたのは §4 の手入力導線のためで、**現在これが許容できるのは、部屋が一時的であり、
かつ見る側と見られる側が同一人物という前提（§3-3）があるからに過ぎない。**
他人に部屋を見せる段階へ進む前に、必ずこの判断を見直すこと。

### その他

- **TURNサーバー未設置。** 同一LANならP2Pはほぼ成功するが、別ネットワーク間や
  symmetric NAT では中継が要る。現在は失敗時に理由を表示するのみ（無音で失敗させない）
- **ゲスト枠が free(500)。** 匿名ユーザーは作り放題なので乱用対策が要る
- **レート制限がGatewayに無い**（プロバイダの429転写のみ）
