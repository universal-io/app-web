## 2026-08-20 — 実機サインインが通った（2つの穴を塞いでから）

`/solo` からのGoogleサインインが実機で通しで成功。あわせてサインインの形を

### 間違えた記録: 匿名セッションの残骸が壁を素通りした

匿名サインインを廃止した後も、**廃止前にブラウザへ作られた匿名セッションは
localStorage に残って自動更新され続けていた**。壁は「セッションがあるか」しか
見ておらず、その持ち主はサインイン画面を一度も見ずに質問まで到達できた。
「認証を入れた」というコミットの直後に、認証なしで使える実機が存在していた。

対処: 判定を `signedIn()` の1箇所に集約し、匿名は「サインイン済み」と見なさず、
検出したら自動サインアウトで掃除する。**機能を廃止しても、その機能が配った
資格情報は各ブラウザの中で生き続ける** — 廃止とは発行を止めることであって、
回収ではない。

### 間違えた記録: `redirect_to` のクエリが全サインインを別サイトへ流した

Redirect URLs に `http://localhost:7380/auth/callback` を登録済みだったが、
実際に送っていたのは `…/auth/callback?next=/solo`。Supabase の照合は
**文字列全体のglob**なので不一致となり、**黙って Site URL
（`api.universal-io.com` — Mac版の着地点）へフォールバック**した。トークンは
URLフラグメントに載って別オリジンへ届き、app-web にはセッションが残らない。
症状は「何度サインインしてもループする」で、成功と失敗が同じ顔をしていた。

対処: `redirect_to` は登録値とバイト同一に保ち、戻り先は sessionStorage で運ぶ
（`consumeNext`）。ダッシュボードの変更は不要だった。

### 間違えた記録: 検証が旧仕様を前提にしていた

check-solo-buffer の「サインインしていない」検査は「壁が出ること」を確認していた。
仕様をボタン時サインインに変えた時点で、この検査は**古い設計の番人**になっていた。
検査も仕様の一部であり、仕様を変えたら検査の主張も書き換える。

### 間違えた記録: アクセストークンをページ読み込み時に取ったきり使い回した

質問すると「ログインが必要です。もう一度サインインしてください」と出た。**このプロダクトに
ログイン画面は無い**ので、案内として成立していない。原因はSupabaseのアクセストークン
（有効期限約1時間）をマウント時に1度取ってReactの状態に持ち続けていたこと。クライアントは
裏で更新していたのに、送っていたのは古いほうだった。タブを開きっぱなしで使う設計なので、
放置すれば必ず起きる。リクエストのたびに取り直すよう変更。

### 間違えた記録: 静止させるボタンを作った

「この画面について聞く」を押さないと質問モードに入らない形にしていた。ライブ映像に
指した対象は答えが返るまでに動くので静止画が要る、というのは**こちらの都合**であって、
ユーザーに踏ませる手順ではない。**そもそもこのモードでは見る側と見られる側が同一人物
なので、勝手に画面が流れることが起きない。** 切り出す瞬間はユーザーが行動した瞬間でよく、
クリック・丸囲みならジェスチャー開始時、質問なら送信時。ボタンは消えた。

### 間違えた記録: 覆いを「色を乗せる」で作った

半透明の青＋中心に白い光、という作りにしていた。**暗いページを共有すると効果が
反転する。** 青は真っ黒より明るいので周囲が暗くならず、代わりに白い光が
「一番よく見せたい場所」だけを曇らせる。変数は我々の配色ではなく、**映っている
他人の画面の明るさ**だった。

`backdrop-filter: brightness()` に変更。下にあるものへの相対なので白でも黒でも
同じように暗くなる。スポットライトは覆いを `mask-image` で抜く形にして、
**芯には何も足さない**（光らせるのではなく、そこだけ手を加えない）。

### 分かったこと: 背面ウィンドウにはマウス移動が届かない（macOS）

スポットライトが、別ウィンドウで作業中はカーソルに付いてこない。正確には
**入った瞬間に一度だけ動いて、そこで止まる**。macOS が連続的な mouse-moved を送るのは
キーウィンドウだけで、背面には境界イベントしか届かないため。OSレベルの制約なので
回避できない。**居場所について嘘をつく光は光が無いより悪い**ので、フォーカスが無い間は
スポットライトを消して一様な青にした。

なお最初は「絵の要素に pointermove を付けていたから」という別の原因も重なっていた。
window で拾うよう直した結果、余白の上でも追従するようになっている。

### 分かったこと: 匿名サインインにはIP単位のレート制限がある

検証スクリプトを続けて走らせると Supabase が 429 を返し、セッションが作られず、
**「回答が出ない」という別の故障の顔で現れた**。検証側はブラウザコンテキストを
使い回して回避したが、**製品側でも同じことが起きうる**（同一NAT配下の多人数）。
乱用対策と併せて扱うこと（two-device-mode.md §5）。

### 間違えた記録: onClick に渡したハンドラがクリックイベントを受け取った

「聞く」を押すと必ず「エラーが発生しました」。Enterキーなら通る。原因は
`<button onClick={onSubmit}>` で、`onSubmit` が省略可能な引数を取るように変わった
（`ask(about?: Capture)`）ため、**クリックイベントが画像の位置に入っていた**。
`() => void` はイベントハンドラに代入可能なので、TypeScriptには見えない。
`onClick={() => onSubmit()}` と書けば起こらない。

この経路に検証が無かったのが本当の原因なので、Gatewayをスタブして「押す→送る→
回答が出る→枠が描かれる」までを常時検証するようにした。

### 間違えた記録: 動画と静止画で箱の形が変わった

ライブは領域に合わせて縮小、静止画は横幅いっぱいのスクロール領域、と別々に組んでいた。
**タップした瞬間に対象が242px動く**ので、狙いを外したように感じられる。同じ箱に重ねて
描くよう変更（ズレ 0.5px）。

箱の寸法は **CSS ではなく実測で決める**。`aspect-ratio` に max-width / max-height を
組み合わせる書き方は、箱の中身が全て絶対配置でフローに何も無いため寸法が決まらず、
静かに破綻した。ResizeObserver で領域を測って px で与える。

### 間違えた記録: 「ライブに戻る」ボタンを置いた

モードが1つ増えると *ライブとは何か* を説明する責任が生まれる。ユーザーから見れば
自分の画面が映っているだけで、動くか止まるかは内部の都合。「新しく聞く」に畳んだ。
なお畳んだ直後、タップして静止したあと戻る手段が無くなっていた（会話が始まるまで
ボタンが出ない条件だった）ので、取り消せるものがあるときは常に出すよう修正。

### 間違えた記録: `<video>` を三項演算子の両側に置いた

ライブ表示と縮小表示で別々の `<video ref={videoRef}>` を書いた。React は位置と型で
照合するため**アンマウントと再マウントが起き、新しい要素には srcObject が無い**。
「ライブに戻る」で真っ黒になる。要素は1つにして class だけ変える。

あわせて、要素に `object-contain` でレターボックスを出すと座標計算にその分の補正が
要る。**箱のほうを映像の縦横比にすれば補正自体が不要**になる（`aspect-ratio` を親に
与える）。補正のズレは0.0pxで通っていたが、要らない計算は消したほうが安全。

### 間違えた記録: 離席判定に `document.hasFocus()` を使った

画面全体を共有した直後から、**ユーザーがどこにも移動しないうちに合わせ鏡が量産された。**
スクリーンショットでは入れ子が4段以上あった。

原因は離席判定を `document.hidden || !document.hasFocus()` にしていたこと。「別アプリが
手前に来た状態も離席と同じ」と考えたが、**画面全体共有では「フォーカスが無いが画面には
映っている」＝写るのは自分**である。しかもChromeの「画面を共有しています」バーは独立した
ウィンドウで、共有開始と同時にフォーカスを奪う。つまり撮影は即座に始まっていた。

`document.hidden` のみに変更。代償として、別アプリを手前に出しただけでは何も記録されない。

## 2026-08-15 — ブラウザ経路の実測（app-ios の試作にて）

判定基準は app-ios M4 がネイティブ伝送路に課したものを流用: **片道300ms以内・
文字が読める**。

| 項目 | 実測値 | 判定 |
|---|---|---|
| 片道遅延（安定後） | 40〜150ms | ✅ 300msに対し余裕あり |
| 可読性 | 日本語UIの小さな文字まで判読可能 | ✅ |
| 送信レート（タブ前面時） | 14.7 fps（設定15） | 設定どおり |
| 送信レート（**タブ背面時**） | **きっかり 1.0 fps** | 🔴 タイマー間引き |
| 帯域（JPEG方式） | 6.1 Mbps で 3.6 fps | H.264の約3倍非効率 |

試作はJPEGをHTTPで1枚ずつ運ぶ足場であり、製品の伝送路ではない。上の数字は
ブラウザ経路のコストの**上限**で、上限で合格したので問いは片付いた。

**未解明が1つ残っている**: 遅延が40msから1000ms超まで単調に増えてから回復する現象。
フレームサイズと相関していた。有力仮説は「間引かれたタブでの重いJPEG変換」だが未確認。
WebRTC移行でこの機構自体が消えるため深追いしなかったが、**「遅延が無限に伸びる」は
app-ios M4 で致命的と判定した症状**。再発したらここに戻ること。

### 間違えた記録: web固有の授業料（すべて例外を投げず、正解の顔をして間違えた）

| 罠 | 対処 |
|---|---|
| `getDisplayMedia` は secure context のみ。LAN IPのhttpでは共有ボタン自体が出ない | 開発は `localhost`、配布はHTTPS必須 |
| 背面タブのタイマーは毎秒1回に間引かれる（15fps設定→きっかり1.0fps） | JSタイマーでフレームを刻まない |
| `display:none` の `<video>` はデコードが保証されない | 小さく表示し続ける（取得が生きている証拠も兼ねる） |
| idセレクタの `display` 指定が `[hidden]` に勝つ。ボタンは反応するのに画面が変わらない | `[hidden] { display: none !important }` をリセットに入れる |
| 中継が古いフレームを「生きている映像」の顔で返す | 鮮度チェックで保留に切り替える。古い絵は無いより悪い |
| 計測器がゼロの列を出すと「経路が死んでいる」と誤読される。実際は送信側を起動していなかっただけ | 計測器は状態を言い、無データの要約を拒否する |
| 3001番ポートが別プロジェクトに占有され、無関係なアプリが表示された | 7380 を使う（`IO` = 73,79 由来） |
