# Universal I/O for Web（仮称）

**ブラウザだけで、いま見ている画面を分かってくれる相棒。**
インストールも設定もなく、リンクを開いて画面を共有すれば、AIが画面を読み、
質問に答え、次の一手を案内する。

タグラインは本家と同じ「**心に、眼鏡と杖を。**」。仕事をする上での様々なギャップ —
知識・経験・言語・文化だけでなく、認知特性や能力のギャップ — を埋める眼鏡のような
補助具を目指す。行政手続きが分からない高齢者、仕事を始めたばかりの若い人、何らかの
ビハインドを持つ人が使えること。同時に、能力の高い人がさらにハイパフォーマンスを
発揮するためのエンパワーメントでもあること。**補助具は当事者だけのものにした瞬間に
普及しない。眼鏡のように全員のものにする**（app-mac の投資家ピッチと同じ立場）。

**状態: M2（2台構成）が実機で動作。精度に既知の問題が残っている。**

本番: <https://universal-io-app-web-kaya-matsumotos-projects.vercel.app>

PCで共有 → QRまたは8文字コードでスマホが参加 → ミラーを見て、聞きたい瞬間に固定 →
なぞって囲む／タップ → 解説と枠。ここまで実機で通っている。
**次に着手すべきことは下の「残課題」を正本とする。**

```bash
npm install
cp .env.example .env.local   # Supabaseの2値を埋める
npm run dev                  # http://localhost:7380
```

**ログイン画面は無い。** ページを開くと匿名サインインでセッションが張られる。
Gatewayは全AI routeでBearerトークンを要求する（それが課金計測とAPIキー秘匿の担保
なので迂回しない）が、「認証が要る」と「ログインさせる」は別であり、匿名セッションなら
ユーザーは何も入力しない。

前提として **Supabase の Authentication → Sign In / Providers で
「Anonymous sign-ins」を有効にする**必要がある。無効だとページに理由が表示される。
匿名ユーザーも `bs_provision_user` により通常どおり personal テナント＋free プランで
プロビジョニングされるので、マイグレーションは不要（枠を絞る `guest` プランは
公開時の乱用対策で、docs/requirements.md §5-D）。

Gatewayは既定で本番（`api.universal-io.com`）を見る。`localhost:7380` はGateway側の
CORS許可リストに入っている。

### ポート番号（7380）について

3000〜3010 は create-next-app・Vite・Express の既定値で、**JSエコシステム全体が
取り合う帯域**である。実際、app-webを最初に起動したとき3001は別プロジェクト2つに
占有されており、画面には無関係なアプリが表示された（起動失敗が「動いているように
見える」形で現れる、たちの悪い症状）。

そのため universal-io ファミリーは 10000未満で衝突しない帯を使う。基点は `IO` の
ASCIIコード（73, 79）から `7379`。

| ポート | 用途 |
|---|---|
| 7380 | **app-web（このリポジトリ）** |
| 7379 | Gateway をローカルで動かす場合の予約（既定は本番を見るので通常不要） |

macOSでは 5000・7000 を AirPlay Receiver が使い、49152以降はOSが外向き接続へ
割り当てるため、いずれも避ける。

## プロダクト定義（ブレスト段階のスナップショット）

**オンライン会議の画面共有と同じ操作で、AIに画面を見せる。**

1. ブラウザでページを開く（インストールなし。これが製品の存在理由）
2. 「画面を共有」を押すと、OS標準のピッカーが出る — 画面全体・ウィンドウ・タブから選ぶ
3. 共有した画面について、クリックや丸囲みで場所を指し、テキストや音声で質問する
4. AIが解説し、押すべき場所を（共有画面のスナップショット上に）示す
5. 終わったらタブを閉じる。何も残らない

ZoomやMeetで誰もが体で覚えた操作体系をそのまま借りる。教えることがゼロで、
「このウィンドウだけ共有」という**プライバシーの文法**まで一緒に借りられる。

### 利用形態は同じ仕組みの上に3つ

| 形態 | 構成 | 特徴 |
|---|---|---|
| **PC内完結** | 1台のPCの中で画面共有＋コパイロットパネル | ストリーミング不要（質問の瞬間に1フレーム取ればよい）。最も軽い |
| **別デバイスパネル** | PCの画面をタブレット/スマホで見ながら質問 | 作業画面を1ピクセルも奪わない |
| **アンビエント**（将来） | 音声＋VADで常時待機。「このメール何て言ってる？」 | 会議の同席者のように振る舞う |

## プロダクトファミリー内の位置づけ

| | app-mac（本家・配布済み） | app-ios | **app-web（本企画）** |
|---|---|---|---|
| 導入 | DMGインストール＋権限設定 | App Store（予定） | **URLを開くだけ** |
| 対象OS | macOS | iOS/iPadOS | **すべて**（Windows含む） |
| 召喚 | ホットキーで即時 | アプリ起動 | タブを開いて共有（数秒の儀式） |
| 画面の取得 | ScreenCaptureKit | カメラ / ミラー受信 | `getDisplayMedia` |
| AX実測座標 | ✅ | ミラー時のみ（M5予定） | ❌（画像のみ） |
| 実画面へのオーバーレイ | ✅ | ✅（ミラー映像上） | ❌（スナップショット上に描く） |
| 将来のリモート操作 | 設計済み | — | ❌（ネイティブ連携で解錠の可能性） |

**web版はネイティブ版の代替ではなく、カバレッジの拡張である。**
ネイティブが勝ち続ける点（ホットキーの召喚速度、実画面オーバーレイ、AX、操作）は
構造的なもので、web版はそこを追わない。逆にweb版だけが持つもの — 準備ゼロ・全OS・
URLで配布（＝URLにコンテキストパックを紐づければ「うちの社内システム用コパイロット」
が配れる）— がネイティブには構造的に持てない。**初期フェーズはweb版を先行させる**
（判断の根拠は inception.md §5）。

## 変わらない規則（ファミリー共通）

- **AIプロバイダのAPIキーをクライアントに置かない。** モデル呼び出しは必ず自前サーバー経由
- **モデルを知るのはサーバーの1ファイルだけ**
- **どの操作も無音で終わらない** — 有限時間で結果か、原因を述べるエラーに到達する（app-mac R11）
- **ユーザーの明示操作（クリック・丸囲み・質問）が回答スコープを決める。** 周辺情報に上書き権限はない
- **注入している知識（パック/Skill）は必ずUIに表示する。** 見えない知識は疑うことも直すこともできない
- **画面画像・回答は保存しない**。usageには運用情報だけ（app-mac のデータ保存方針を踏襲）
- **測ってから決める**

## 残課題（2026-08-16 時点。次のセッションはここから）

### 🔴 1. 座標精度 — 未解決。次にやるべきはこれ

タップ・囲みで指した対象と、返ってくる枠・解説が一致しないことがある。
**このセッションの最後に「画像サイズをモデルへ伝える」修正を入れたが、その効果は
未検証。まず実機で確認すること。**

**⚠️ 着手前に必ず読む（このセッションで読まずに再発明した）:**

- `../app-ios/docs/investigation-highlight-offset.md` — 同じ症状の調査記録。**解決済み**
- `../app-ios/docs/lessons-from-app-mac.md` §3〜§4 — 座標の授業料。実測値つき

要点（推測で作業を始めないこと）:

| 事実 | 現状 |
|---|---|
| 画像サイズを伝えないと縦誤差0.155。伝えると0.001 | ✅ 2026-08-16に実装（`api-gateway/lib/server/image-size.ts`、app-iosから移植）。**効果未検証** |
| 長辺1536以下に縮小 | ✅ 実装済み（`lib/screen-share.ts`） |
| 誤差はバイモーダル。**定数オフセット補正は最悪手**（当たっている回を壊す） | — 補正は入れていない。入れないこと |
| **最終解は実測への接地**（`candidates` に実測矩形を渡す） | ❌ **未実装。ブラウザにOSのOCRが無い** |

最後の項目が本丸。app-ios は `VNRecognizeTextRequest` で解決し、モデルが+0.049外した
プルダウンを+0.002で捉えた。**接地の価値は精度そのものより、精度が画像サイズ・解像度・
画角から独立することにある。** web版の選択肢は (a) WASM OCR をクライアントで動かす
(b) Gateway側でOCR (c) 当面モデルの目測のまま。未決。

なお **AX/DOMは一切使っていない**（`candidates` は常に空）。挙動がAXっぽく見えても
実体はビジョンのみ。

### 2. 検証の道具が無い

app-ios は「**サーバーが受け取ったバイトに、サーバーが返した座標で枠を描く**」道具
（`UIO_DEBUG_CAPTURE_DIR` ＋ `draw-boxes.py`）で1枚で決着させた。
**web版には同等の手段が無く、ブラウザ越しの目視でしか判定できない。**
investigation §7 の「仮説を立てる前に絵を見る手段を作る」がまだ守れていない。

### 3. UX

- 説明パネルが下部固定。回答が長いとスクロールが要る
- 「ライブに戻る」以外に、固定したまま撮り直す導線が無い
- PC側（共有側）の画面は最低限のまま

### 4. 公開前に必須（今は意図的に保留）

- **部屋コードが約39bit**。総当たり可能。§10「公開前に必ず戻ること」を参照
- **TURNサーバー未設置**。別ネットワーク間では繋がらない（理由は表示される）
- **ゲスト枠が free(500)**。匿名ユーザーは作り放題なので乱用対策が要る（§5-D）
- レート制限がGatewayに無い（プロバイダの429転写のみ）

### 5. Gateway側の未着手（docs/requirements.md §5）

- **§5-E 画像からの製品判定** — Skillの `detect` は `host`/`bundle_id` 依存で、
  web版では発火しない。Slack・GA4等の知識が注入されないまま
- **§5-F 契約のバージョニング規律** — `focus_target`／`visual_selection_hint`／
  `selection`／`pointer` と4世代が同居している
